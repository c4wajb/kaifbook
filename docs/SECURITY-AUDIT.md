# Отчёт по безопасности — Kaifbook

## Сводка

Проведён аудит веб-приложения Kaifbook. Всего подтверждено **26 находок**. Распределение по уровню критичности:

| Уровень | Кол-во | Эксплуатируемо |
|---|---|---|

| Средние | 6 | 6 (1 — практ. неэксплуатируема) |

| Информационные | 0 | — |

**Общая оценка риска: ВЫСОКАЯ.**

Ключевая проблема — связка из двух факторов: (1) хардкоженный fallback-секрет `local-dev-secret-change-me`, используемый для подписи JWT и шифрования при отсутствии переменной окружения, и (2) утечка `VK_CONFIRMATION_CODE` без аутентификации. Первая позволяет подделать сессию любого пользователя (включая администратора) при любой ошибке конфигурации production. Дополнительно вся группа публичных эндпоинтов (логин, регистрация, бронирования, лиды, верификация) не имеет защиты от перебора, а вебхук VK реализован менее безопасно, чем эталонный вебхук MAX в этом же проекте (fail-open вместо fail-closed, сравнение секрета без защиты от тайминг-атак). Серия IDOR в публичном платёжном контуре раскрывает суммы, URL платежей и `confirmationToken` без авторизации.

Приоритет на исправление: сначала два критических пункта, затем секреты вебхука VK и отсутствие rate-limiting на аутентификации.

## Критические

### 1. Раскрытие кода подтверждения вебхука VK без аутентификации
- **Категория:** Раскрытие информации без аутентификации
- **Критичность:** Критическая · **Эксплуатируемо:** Да
- **Файл:** `src/app/api/webhooks/vk/route.ts` (строки 13–18)
- **Что не так:** В обработчике `POST` проверка `type === "confirmation"` (строка 16) и `return process.env.VK_CONFIRMATION_CODE` (строка 17) выполняются **до** вызова `hasValidSecret` (строка 19). Проверка подписи для запроса типа `confirmation` недостижима — `return` срабатывает раньше.
- **Как эксплуатируется:** Любой неаутентифицированный атакующий отправляет `POST /api/webhooks/vk` с телом `{"type":"confirmation"}` и получает `VK_CONFIRMATION_CODE` в ответе. Этот код — общий секрет проверки подлинности вебхуков VK; его раскрытие позволяет атакующему формировать «легитимные» payload'ы вебхука с валидной подписью.
- **Исправление:** Изменить порядок: сначала `hasValidSecret`, при невалидной подписи — `403`; только при валидной подписи и `type=confirmation` возвращать код; при `type=event` — обрабатывать событие. Проверка секрета должна предшествовать любой выдаче кода.

### 2. Хардкоженный fallback-секрет в операциях с JWT
- **Категория:** Слабые учётные данные по умолчанию
- **Критичность:** Критическая · **Эксплуатируемо:** Да
- **Файлы:** `src/lib/auth.ts:13`, `src/app/api/vk-mini/session/route.ts:13`, `src/lib/vkid-auth.ts:86`
- **Что не так:** Строка `"local-dev-secret-change-me"` используется как fallback при незаданных `SESSION_SECRET` / `VK_APP_SECRET`. Подтверждено в коде: `return encoder.encode(process.env.SESSION_SECRET ?? "local-dev-secret-change-me")`. Этим секретом подписываются JWT аутентификации и сессии VK Mini App. Валидации на старте приложения нет — при отсутствии переменной приложение молча использует известный секрет.
- **Как эксплуатируется:** При любой ошибке конфигурации (dev/staging/production) подпись выполняется публично известным секретом. Атакующий, знающий эту строку, подделывает валидный JWT и выдаёт себя за любого пользователя, включая администратора, получая полный доступ к защищённым эндпоинтам и данным.
- **Исправление:** Убрать fallback полностью; при незаданных `SESSION_SECRET` / `VK_APP_SECRET` бросать ошибку на старте (fail-fast). Добавить валидацию конфигурации перед запуском. В dev использовать сильный случайный секрет из `.env` (не коммитить).

## Высокие

### 3. Хардкоженный `SESSION_SECRET` со слабым значением по умолчанию
- **Категория:** Аутентификация · **Эксплуатируемо:** Да
- **Файл:** `src/lib/auth.ts:12-14`
- **Что не так:** Тот же fallback `"local-dev-secret-change-me"` в `getSecret()`. Это конкретное проявление пункта 2 в основном модуле аутентификации.
- **Как эксплуатируется:** Если в production `SESSION_SECRET` не задан, JWT подписываются известной строкой → подделка сессии любого пользователя.
- **Исправление:** Сделать `SESSION_SECRET` обязательным в production (ошибка при отсутствии), длиной от 32 символов, генерируемым при деплое. Валидация на старте.

### 4. Слабый fallback `SESSION_SECRET` в шифровании VK ID
- **Категория:** Криптография · **Эксплуатируемо:** Да
- **Файл:** `src/lib/vkid-auth.ts:85-87`
- **Что не так:** `encryptionKey()` = `createHash("sha256").update(process.env.SESSION_SECRET ?? "local-dev-secret-change-me").digest()`. Этим ключом шифруются данные сессии верификации VK ID, включая PKCE code verifiers.
- **Как эксплуатируется:** При незаданном `SESSION_SECRET` атакующий с доступом на чтение БД расшифровывает все сохранённые code verifiers и может перехватить OAuth-поток (через полученные authorization codes).
- **Исправление:** Обязательная валидация `SESSION_SECRET`; никаких хардкоженных дефолтов для криптографии.

### 5. Отсутствие защиты от перебора на эндпоинте логина
- **Категория:** Аутентификация · **Эксплуатируемо:** Да
- **Файл:** `src/app/api/auth/login/route.ts`
- **Что не так:** В обработчике `POST` нет rate-limiting, блокировки аккаунта, CAPTCHA или экспоненциальной задержки. Библиотек rate-limit в зависимостях нет, middleware эндпоинт не защищает.
- **Как эксплуатируется:** Неограниченный перебор паролей по известным/перечислимым email. `bcryptjs` замедляет одну попытку, но тысячи параллельных запросов в минуту ничем не сдерживаются.
- **Исправление:** Rate-limiting по IP и по email (напр. 5 неудачных попыток / 15 мин), блокировка аккаунта после N попыток, опционально CAPTCHA / экспоненциальная задержка.

*(Примечание: пункты 5 и пункт «No rate limiting on password login endpoint» из исходных данных описывают один и тот же эндпоинт `login` — объединены здесь во избежание дублирования.)*

### 6. Вебхук VK: сравнение секрета без защиты от тайминг-атак
- **Категория:** Тайминг-атака · **Эксплуатируемо:** Да
- **Файл:** `src/app/api/webhooks/vk/route.ts:10`
- **Что не так:** `return (payload as {...}).secret === expected;` — обычное сравнение строк `===` вместо constant-time. Вебхук MAX (`max/route.ts`) и `vk-mini/session/route.ts` корректно используют `crypto.timingSafeEqual` — проект знает о проблеме, но в вебхуке VK она не применена.
- **Как эксплуатируется:** Измеряя время ответа на запросы с разными секретами, атакующий побайтово восстанавливает `VK_CALLBACK_SECRET` и затем подделывает события вебхука.
- **Исправление:** Заменить `===` на `timingSafeEqual` (как в `max/route.ts`), сравнивая байтовые представления.

### 7. Вебхук VK: приём любых запросов при незаданном секрете (fail-open)
- **Категория:** Небезопасные значения по умолчанию · **Эксплуатируемо:** Да
- **Файл:** `src/app/api/webhooks/vk/route.ts:8`
- **Что не так:** `if (!expected) return true;` — при отсутствии `VK_CALLBACK_SECRET` принимаются **все** запросы. Вебхук MAX в той же ситуации возвращает `false` (отклоняет).
- **Как эксплуатируется:** При неполной конфигурации production атакующий отправляет события вебхука без секрета; обработчик инициирует выдачу кодов верификации и сообщения. Публичные коды короткие (алфавит ~34 символа, ~1.3 млн комбинаций) и поддаются перебору.
- **Исправление:** Заменить на `if (!expected) return false;` — fail-closed: при отсутствии секрета отклонять запросы.

*(Примечание: исходные находки «Allows All Requests When Secret Not Configured» и «Accepts Any Payload When Secret Not Configured» описывают этот же баг строки 8 — объединены.)*

### 8. IDOR: неаутентифицированный доступ к платёжным данным бронирования
- **Категория:** Авторизация / IDOR · **Эксплуатируемо:** Да
- **Файл:** `src/app/api/public/reservations/[reservationId]/pay-deposit/route.ts`
- **Что не так:** `POST` принимает `reservationId` из URL без аутентификации и возвращает `paymentRequired`, `paymentStatus`, `paymentAmount`, `paymentUrl`. Нет `getCurrentUser()` / `requireAuth()` / проверки владения.
- **Как эксплуатируется:** Перебор CUID-идентификаторов бронирований (не являются секретом) → раскрытие сумм, URL платежей (с внутренними `payment.id`) и статусов для всех бронирований.
- **Исправление:** Требовать либо аутентификацию с проверкой владения по `userId`, либо валидный `confirmationToken`, совпадающий с бронированием, до возврата платёжных данных.

### 9. IDOR: неаутентифицированный доступ к платежу и данным бронирования
- **Категория:** Авторизация / IDOR · **Эксплуатируемо:** Да
- **Файл:** `src/app/api/public/payments/[paymentId]/status/route.ts:6-18`
- **Что не так:** `GET` принимает `paymentId` без аутентификации и возвращает полный объект платежа с вложенным `reservation`, включая чувствительный `confirmationToken`.
- **Как эксплуатируется:** Цепочка: получить `payment.id` (через свой заказ или из `paymentUrl` пункта 8) → запросить этот эндпоинт → собрать суммы, даты, статусы и `confirmationToken`. Полученный токен пригоден для дальнейших атак.
- **Исправление:** Аналогично пункту 8 — проверка владения по `userId` либо валидный `confirmationToken` до возврата данных; не включать `confirmationToken` в публичный ответ.

### 10. Отсутствие rate-limiting на эндпоинте регистрации
- **Категория:** Rate Limiting и спам · **Эксплуатируемо:** Да
- **Файл:** `src/app/api/auth/register/route.ts`
- **Что не так:** В `POST` нет rate-limiting, CAPTCHA, верификации email и IP-throttling. Сообщения об ошибках различают «email/телефон уже существует».
- **Как эксплуатируется:** Неограниченная регистрация фейковых аккаунтов и перечисление пользователей (user enumeration) по разнице в ответах.
- **Исправление:** Rate-limiting по IP (5–10 регистраций/час), верификация email до активации, единые сообщения об ошибках, опционально CAPTCHA.

### 11. Обход IP-rate-limiting через подмену заголовка `x-forwarded-for`
- **Категория:** Обход Rate Limiting · **Эксплуатируемо:** Да (зависит от деплоя)
- **Файл:** `src/lib/verifications.ts:559-562`
- **Что не так:** `requestIp()` берёт `x-forwarded-for` / `x-real-ip` без валидации и доверенного прокси; значение используется в подсчёте лимита (строка 194).
- **Как эксплуатируется:** При прямом доступе к приложению атакующий подменяет заголовок, обходя per-IP лимит (30 запросов / 10 мин) в `/api/verifications/start`. Митигировано, если приложение строго за доверенным reverse-proxy; уязвимо при любой неверной конфигурации, где приходят недоверенные заголовки.
- **Исправление:** Доверять `x-forwarded-for`/`x-real-ip` только от whitelisted доверенных прокси (список в env); для прямых соединений использовать `remoteAddress`. Дополнительно ужесточить лимит по номеру телефона.

## Средние

### 12. Хардкоженный `VK_APP_SECRET` в `.env`
- **Категория:** Управление секретами · **Эксплуатируемо:** Нет (практически)
- **Файл:** `.env:7` — `VK_APP_SECRET="***REDACTED***"`
- **Что не так:** Секрет VK Mini App присутствует в `.env` в открытом виде.
- **Как эксплуатируется:** Знание секрета позволяет подделать подпись launch-параметров VK Mini App. Однако привилегии не повышаются: результирующий `sessionToken` хранится только в client-side React state и **нигде не валидируется на сервере**; создание бронирования подпись не требует, поле `source` — только для логов. Тем не менее секрет в репозитории — серьёзное нарушение практик.
- **Исправление:** Немедленно ротировать `VK_APP_SECRET` в кабинете VK. Не хранить секреты в `.env` в репозитории; использовать секрет-менеджер или runtime-инъекцию; в репозитории — только `.env.example` с плейсхолдерами.

### 13. Open Redirect через невалидированный параметр `next` в логине владельца
- **Категория:** Open Redirect · **Эксплуатируемо:** Да
- **Файлы:** `src/components/AuthForm.tsx:49`, `src/app/owner/login/page.tsx:14`
- **Что не так:** `nextPath` из `searchParams` передаётся в `router.push(nextPath)` без валидации. В отличие от guest-логина (`safeNextPath()` в `guest/login/page.tsx:7-10`), owner-логин такой защиты не имеет.
- **Как эксплуатируется:** Ссылка `/owner/login?next=https://attacker.com` или `?next=//attacker.com` → после входа владельца перебрасывает на сайт атакующего (фишинг учётных данных/токенов).
- **Исправление:** Применить серверную валидацию `next` (как `safeNextPath()`): разрешать только пути, начинающиеся с одного `/`, отклонять protocol-relative (`//`) и абсолютные URL со схемой — до передачи в `AuthForm`.

### 14. Отсутствие rate-limiting на публичном эндпоинте создания бронирований
- **Категория:** Rate Limiting и спам · **Эксплуатируемо:** Да

- **Как эксплуатируется:** Неограниченные фейковые бронирования с разными номерами → флуд очереди бронирований и системы уведомлений ресторана (DoS / срыв работы).
- **Исправление:** Rate-limiting по IP (напр. 3 бронирования/час) и по номеру телефона; требование кода верификации до подтверждения; CAPTCHA при подозрительных паттернах.

### 15. Отсутствие rate-limiting на публичной отправке лидов (лендинг)

### 16. Отсутствие rate-limiting на отправке лидов ресторанов

### 17. Слишком разрешающие CORS-заголовки на эндпоинте OpenAPI

- **Исправление:** Убрать заголовок `Access-Control-Allow-Origin` полностью, либо ограничить доверенными origin (`https://www.kaifbook.ru`); рассмотреть закрытие спецификации аутентификацией, если она не публична.

## Низкие

### 18. Невалидированный числовой параметр без проверки границ
- **Категория:** Валидация ввода · **Эксплуатируемо:** Да
- **Файлы:** `src/app/api/public/restaurants/route.ts:12`, `src/app/api/restaurants/route.ts:8`, `src/lib/public-data.ts:60`
- **Что не так:** `Number(searchParams.get("averageCheck") || 0)` без проверки границ принимает `Infinity` / `1e308`.
- **Как эксплуатируется:** Передача `averageCheck=Infinity` вызывает ошибку преобразования типа в БД → ответ `500` (DoS на уровне ошибок). Данные не утекают, доступ не повышается — отсюда низкая критичность.
- **Исправление:** Валидировать через zod: `z.coerce.number().int().min(0).max(1000000).default(0)`; либо проверка `Number.isFinite` (как уже сделано в availability-route).

### 19. Невалидированный параметр `status` в запросах бронирований
- **Категория:** Валидация ввода / целостность данных · **Эксплуатируемо:** Нет
- **Файл:** `src/app/api/owner/restaurants/[restaurantId]/reservations/route.ts:7`
- **Что не так:** `status` из `searchParams` передаётся в `prisma.findMany` без проверки против `RESERVATION_STATUSES`.
- **Как эксплуатируется:** Не эксплуатируемо: эндпоинт за `requireStaffOrOwnerAccess()`, Prisma параметризует запрос, невалидный статус даёт пустой результат, а не утечку. Вопрос качества кода.
- **Исправление:** Валидировать `status` против `RESERVATION_STATUSES` и возвращать `400` при невалидном значении.

### 20. Невалидированный параметр `status` в запросах лидов
- **Категория:** Валидация ввода / целостность данных · **Эксплуатируемо:** Нет
- **Файл:** `src/app/api/businesses/[id]/leads/route.ts:25-32`
- **Что не так:** `status` из URL передаётся в `prisma.lead.findMany` без проверки enum.
- **Как эксплуатируется:** Требует аутентификации и владения бизнесом; невалидные значения дают пустой результат. Минимальное практическое влияние.

### 21. Невалидированный строковый фильтр в поиске гостей (`contains`)

### 22. Невалидированные строковые фильтры в поиске ресторанов (`contains`)

### 23. Слабый fallback-секрет в подписи JWT VK Mini App

### 24. Хардкоженные секреты VK в `.env`
- **Категория:** Хардкоженные секреты · **Эксплуатируемо:** Нет

## Что хорошо

- **Параметризация запросов через Prisma.** Все находки с пользовательским вводом в запросах (`status`, `q`, `cuisine`, `averageCheck`) подтверждённо защищены от SQL-инъекций благодаря параметризации Prisma — это снимает целый класс критических уязвимостей и переводит соответствующие пункты в разряд «качество кода».
- **Структурированные guard'ы авторизации.** Приватные эндпоинты владельца/персонала последовательно используют `requireStaffOrOwnerAccess()` с проверкой принадлежности ресторану — именно это делает пункты 19, 21 неэксплуатируемыми. Проблемы IDOR сосредоточены в публичном (`/api/public/...`) контуре, а не в приватном.
- **Эталон безопасного вебхука уже есть в проекте.** Вебхук MAX (`max/route.ts`) корректно реализует fail-closed при отсутствии секрета и constant-time сравнение через `crypto.timingSafeEqual`; этот же приём применён в `vk-mini/session`. Достаточно перенести готовый паттерн на вебхук VK (пункты 6, 7).
- **Существующая валидация redirect.** Guest-логин уже содержит `safeNextPath()` против open redirect — нужно лишь применить её и в owner-логине (пункт 13).
- **Хеширование паролей.** Используется `bcryptjs`, что замедляет перебор пер-попытку (хотя и не заменяет rate-limiting, пункт 5).
- **Гигиена секретов в VCS.** `.env` корректно в `.gitignore` и не попадал в историю git — это удерживает находки по секретам (12, 24) на уровне «нарушение практик», а не активной утечки.
